# BakeU Backend — первый этап

Общий будущий API для сайта, Android и iPhone: **Node.js 24 + TypeScript + NestJS + PostgreSQL 17 + Drizzle ORM**.
Drizzle генерирует SQL-миграции из TypeScript и не требует отдельного нативного schema engine.

Сейчас реализована основа: конфигурация с проверкой `.env`, HTTP сервер,
точный CORS allowlist, JSON-ошибки, ограничение размера JSON, health/readiness,
OpenAPI/Swagger, подключение PostgreSQL и начальная миграция `users` / `shops`.
Публичных endpoints регистрации, товаров, заказов, оплаты и чата пока нет.
Папки под них подготовлены в `src/modules/`; они не возвращают фиктивный успех.

## Локальный запуск

Нужны Node.js **24 LTS** и Docker Desktop для локального PostgreSQL. Сайт,
мобильное приложение и backend — отдельные npm-проекты.

Из корня BakeU.UZ:

```powershell
cd backend
npm ci
Copy-Item .env.example .env
```

На Mac вместо `Copy-Item` используйте `cp .env.example .env`. Если `.env` уже
существует, сохраните его настройки и не перезаписывайте файл шаблоном.

Затем внутри `backend/`:

```sh
docker compose up -d postgres
npm run db:migrate
npm run dev
```

Открыть:

- HTTP сервер: **http://127.0.0.1:4000/api/v1/health/live**
- База и применённая схема: **http://127.0.0.1:4000/api/v1/health/ready**
- Документация: **http://127.0.0.1:4000/api/docs**
- OpenAPI JSON: **http://127.0.0.1:4000/api/openapi.json**

На Windows можно проверить API:

```powershell
Invoke-RestMethod http://127.0.0.1:4000/api/v1/health/live
```

`live` возвращает 200, когда работает HTTP процесс. `ready` возвращает 503,
если PostgreSQL недоступен или нет начальной таблицы, и 200 после подключения
и миграции. Сервер может работать без доступной базы, но это не означает, что
backend готов принимать бизнес-операции. Остановка: Ctrl+C.

`.env.example` содержит пароль **только для локальной разработки**. База Docker
слушает только `127.0.0.1`. Если меняете `POSTGRES_PORT`, измените порт и в
`DATABASE_URL`. Изменение пароля в `.env` не меняет пароль уже созданной базы.
Данные сохраняются в Docker volume; не удаляйте его для обычного обновления.

## Команды

| Команда               | Назначение                                         |
| --------------------- | -------------------------------------------------- |
| `npm run dev`         | Nest с пересборкой и перезапуском при изменениях   |
| `npm run build`       | TypeScript → `dist/`                               |
| `npm start`           | Запустить готовый `dist/main.js`                   |
| `npm run lint`        | ESLint                                             |
| `npm test`            | Сборка, конфигурация и HTTP-проверки               |
| `npm run check`       | Линтер, сборка и тесты                             |
| `npm run db:generate` | Создать SQL-миграцию после изменения модели        |
| `npm run db:validate` | Проверить согласованность истории миграций         |
| `npm run db:migrate`  | Применить существующие миграции к DATABASE_URL     |
| `npm run db:studio`   | Локальный просмотр базы, без публикации в интернет |

Интеграционный тест реального PostgreSQL включается, если передать
`TEST_DATABASE_URL` с адресом **отдельной тестовой базы**. Он проверяет миграции,
уникальность email/телефона, связь магазина с владельцем и readiness. Без этой
переменной этот тест явно пропускается; остальные проверки базы не требуют.
Тест создаёт и удаляет только свои записи. Запуск с реальным PostgreSQL проверен
в отдельном временном контейнере, а не на данных существующего бота.

## Существующий сайт и бот

- Старый `src/bot/` использует SQLite и HTTP API на **3001**. Его код, данные,
  сессии и Telegram-проверка администратора сохранены.
- Новый backend работает на **4000**, с префиксом **`/api/v1`**. На этом этапе
  его health endpoints ещё не заменяют старые `/api/auth/*` или Mini App endpoints.
- Текущий proxy сайта остаётся направлен на 3001. Не меняйте его на новый API,
  пока не реализованы и не протестированы нужные endpoints.
- Сайт и мобильный каркас пока не переводятся на новую базу автоматически.
  Перенос аккаунтов, сопоставление `client` → `CUSTOMER`, seller/shop IDs и
  совместимость существующих хешей паролей требуют отдельной миграции.
- Роли в схеме — только данные. Они пока не предоставляют права ни одному
  HTTP клиенту. Открытые списки пользователей и выдача admin-токенов не реализованы.

## Дальше

Следующий этап — регистрация/вход, хеширование паролей, сессии и серверная проверка
ролей. Затем магазины/товары и транзакционное оформление по нескольким продавцам.
План: [docs/ROADMAP.md](docs/ROADMAP.md).

Для доступа с других телефонов API нужен постоянный HTTPS сервер и подходящий
CORS allowlist. `localhost` на телефоне указывает на сам телефон. Vercel frontend
сам по себе не запускает этот Node-процесс и PostgreSQL. Приватные ключи бота,
подписи, платёжных провайдеров и `.env` в Git не добавляются. В production задайте
свои DATABASE_URL/CORS_ORIGINS; Swagger по умолчанию выключен.
